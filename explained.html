Plain-English walkthrough

Avensar Signal, explained.

An AI-powered social-listening intelligence service for India — it reads public talk in nine languages plus Hinglish, tells political teams and brands what is rising and how sure we are, and puts a named human analyst behind every number.

Hindi · English · Hinglish · +7 regional languages Aggregate-first · never individuals Analyst-reviewed briefs Working name — trademark pending No code run yet — [UNVERIFIED] claims

The product in one picture

Think of a newsroom clipping service with a smart analyst on staff. A clipping service reads every paper and hands you the relevant cuttings. Avensar Signal does that for public online talk in India — X, YouTube, news sites, and later Threads and a short Instagram/Facebook watchlist. An AI reads each post once; a human analyst then reads the machine output and writes a one-page morning brief.

"We sell an answer, not a login."

The five parts, in plain words

1
Collect
Pull public posts & comments from several sources into one common format.
2
Read
One AI pass per post: language, feeling toward each named party, sarcasm, topic.
3

Report groups, topics and coordinated clusters — never one named person's belief.
4

A light-theme dashboard plus a daily brief at 07:00 IST; every number carries a quality tag.

This is the core loop. Every later step is one slice of these five parts — where data comes from, how the AI reads, how it is stored, what we show, how it is built, and how it is sold.

The 36 decisions (D1–D36)

16 §2 source of truth
File 16 §2 is the source of truth — every other spec file must obey these. Each decision has an ID (D1, D2…) referenced in code and PRs. Grouped into seven themes. (D24 is a stub pointing to D26, so there are 35 real decisions.)

1Red lines — what we will never do

D1Aggregate-first
We report groups, topics and clusters — never what one named person believes, never someone's religion/caste/leaning. Author handles are always scrambled. We detect "coordinated posting", but we never say "this person is a bot".
D11Election embargo
During the 48-hour silence period before polls (and exit-poll windows) we lock anything publishable. A client's internal dashboard stays on; anything public-facing is blocked. We never call our output an "opinion poll".
D12No posting, no bots, ever
We only listen. If we ever generate content for a client, it must be labelled AI-generated and cleared through their pre-certification process.
D14The human analyst is the product
The MVP ships with an analyst workflow (review queue + annotated daily brief), not just a self-serve dashboard. This is what buyers actually pay for.
D36Word analytics stay aggregate too
When we show "what words people use", segments are of posts/conversations, never of people; a word appears only if at least 5 distinct authors used it; exports never include handles.
Takeaway: we listen, we never profile, never post, and a human stands behind everything.

2Where the data comes from

D2Every source is a swappable plug-in
Each platform is a separate adapter that returns the same common format. No business logic depends on one vendor — so when a vendor breaks, we swap it without touching anything else.
D3X data via resellers
twitterapi.io (primary) + SocialData.tools (fallback), because official X is ~$5,000/1M posts vs ~$150–200/1M. This is the one risk you must personally accept (founder decision #1).
D4Instagram/Facebook = watchlist only
We follow a curated list of ~100–300 public accounts/pages — not a hashtag firehose (too risky and costly). For a client's own pages we use their authorized API.
D5Threads keyword search is Phase 1
Official and free (2,200 queries/day), and where Gen-Z talk lives.
Takeaway: cheap, swappable, and conservative — no firehose scraping where it's risky.

3How the AI reads each post

D7LLM-first
One structured AI call per post returns language, sentiment toward each named target, emotion, sarcasm flag, entities and topic. Cheap batch model first; escalate the ~15% that are sarcastic/code-mixed/low-confidence to a stronger model. Only after 3–5k hand-labelled examples per language do we distil into a smaller fine-tuned model.
D8Language detection
Script rules first, then IndicLID, then a Hinglish-specific detector. (We can't use the popular fastText — it's non-commercial.)
D17Vernacular video/audio is Phase 2
Reels/Shorts carry most Bharat discourse, but understanding speech (ASR) is deferred — it's a future differentiator.
D19Language scope = 10 classes
9 languages (Hindi, English, Marathi, Tamil, Telugu, Bengali, Kannada, Gujarati, Punjabi) + the Hinglish register, each with its own test set and gate. Malayalam deferred.
D20Gold-set rules
Our hand-labelled evaluation examples keep text but strip handles; they're only for measuring/tuning, never resold, never used to train foundation models.
D26Emotion = 7 labels
anger, fear, hope/joy, trust, sadness, surprise, none. (disgust/contempt fold into anger; joy folds into hope/joy.) Fewer labels = safer, since humans barely agree on fine-grained emotions.
D27Accuracy gates in one place
File 17 §14.2 is the single home of per-language GREEN/AMBER/RED targets. A language goes live for clients only when it's GREEN.
Takeaway: one AI pass per post, 10 language classes, and we only claim accuracy we've measured.

4Where data lives, and how long

D6Retention per source
YouTube raw text deleted after 30 days; others after 90 days. The scores we derived (no raw text) are kept forever. We honour deletion requests.
D9Boring, cheap database
PostgreSQL + TimescaleDB + pgvector + Redis. Elasticsearch is deferred (saves ~₹5k/month and one service to run).
D10Privacy built to the strict date
We follow the DPDP data-protection law as if fully in force from Nov 2026 — data map, 72-hour breach reporting, 1-year logs, grievance contact, processor agreement.
D25Store each post once, globally
Public posts are collected and stored once (not once per client) — this is what makes the whole thing affordable. One shared key scrambles all author handles. Clients never see the hashes.
D29How deletion actually works
Every post gets an expiry timestamp at insert; a purge job deletes expired raw text and every fragment of it (mentions, embeddings, search index) on schedule.
Takeaway: raw text is short-lived and scrubbed; only anonymous scores persist.

5What the client sees

D13Light theme only
The dashboard is light (warm off-white, orange #DA7756 accent) — a founder rule, and more readable for non-technical clients.
D16Ground-survey overlay
Clients can upload their own field/survey data and overlay it on our social signals — because savvy political buyers distrust social-only numbers.
D18Every number carries a quality tag
Sample size, language reliability, coordination share, sarcasm share — so the client always knows how much to trust a figure.
D21Approval policy
Crisis and data-gap alerts are template-only and can skip review (speed matters). Daily briefs auto-approve only if the client opts in. Weekly/event reports always need analyst approval.
D28Alert rules live in one place
File 07 §2 is the single home of every threshold. (The "Crisis Index" in file 12 is just a dashboard gauge — it never triggers an alert.)
Takeaway: light, honest (quality-tagged), and human-approved before it reaches the client.

6Money & cost control

D23Backfill is paid by us for demos
A 90-day historical backfill for demos comes out of our pocket (~$105–315); for campaign clients it's billed to them.
D34Honest cost accounting
We separate "batch" AI cost (backfill/re-scoring) from "synchronous" (live, ~2× price). Monitoring is simple (Uptime-Kuma); Prometheus/Grafana is Phase 2. Brief timing is fixed: draft 05:30, review 06:00–06:45, out at 07:00 IST.
D35Caps on the expensive stuff
Apify (IG/FB) capped at $120/month. Coordination "author-history" fetches are off by default until budgeted. Synthetic demo data lives in a separate database, never mixed into production.
Takeaway: cost is watched per-vendor, per-cap, and never allowed to silently balloon.

Architecture — how data flows

02_SYSTEM_ARCHITECTURE
The big picture: one app + a queue of workers, with every post flowing through 12 stages.

The big idea

We're building a modular monolith — one application made of interchangeable parts, plus a queue of "workers" doing background jobs. (Not dozens of microservices; those only if we ever get huge.) The cleanest way to understand it is to follow one post on its journey.

The journey of one post (12 stages)

StageWhat happens, in plain words
1 · SchedulerAn "alarm clock" (Celery) wakes a source plug-in on a timer, staying inside its budget.
2 · Fetch + normalizeThe plug-in pulls posts from one platform and converts them into one common shape.
3 · Scrub + hashStrip phone/email/Aadhaar-like numbers; scramble the author's handle with a secret key (count them, don't name them).
4 · DedupeDrop exact duplicates; tag near-duplicates so identical text keeps every row but shares one AI call.
5 · QueuePush the cleaned post into a to-do list (Redis Streams) for workers.
6 · AI reads itDetect language → one LLM call (sentiment/emotion/sarcasm/topic) → escalate the hard ~15% → link entities → tag place → embed meaning.
7 · SaveWrite it into the database with an expiry date on the raw text.
8 · CoordinationEvery 15 min, look for clusters of near-identical text + tight timing.
9 · AggregateRoll up into hourly/daily metrics (volume, sentiment, share of voice…).
10 · AlertCheck the numbers against thresholds; respect the election embargo; fire alerts.

How clients stay separate (multi-tenancy)

Two questions worth pausing on

Why Redis Streams instead of just a database?

A database stores data; a queue distributes work. Redis Streams gives us speed (in-memory), clean multi-worker pull (no two workers grab the same post), burst-buffering, and retries + a dead-letter bin — all things a plain database is bad at. The database is where things end up; the queue is how work flows through.

What does "single tenant" mean?

A tenant = one client. In the MVP we operate one client at a time (manually onboarded and billed). But the data layer is already multi-tenant-ready: public posts are shared-and-global, while each client's private tables (monitors, alerts, reports) are isolated by row-level security. So "many clients" later is a config change, not a rewrite.

How the AI reads it

04_AI_ML_SPECS 17_GOLD_SET_AND_PROMPTS
The "brain" of the product: one AI read per post, tiered, plus the gold set that makes our accuracy honest.

The big idea

Every post gets one AI read, using a tiered approach: a cheap model reads everything; a stronger model re-reads only the hard ~15%; then deterministic code links names, finds places, groups topics and detects coordination. The AI returns a structured answer — not prose — so we can count and aggregate it.

What the AI says about each post

FieldWhat it captures
Language + scriptWhich language, and native / roman / mixed script (e.g. hi + roman = Hinglish)
Content classopinion / news / off-topic / cannot-tell
TargetsFor each named entity: sentiment + stance
Emotion7 labels: anger, fear, hope/joy, trust, sadness, surprise, none
Sarcasmyes / no / unsure + the intended polarity
Topic≤ 4 words ("fuel prices")
Harm flagnone / abuse / hate / threat (for analyst triage)
Confidence + escalationHow sure it is, and why it might be wrong

The key concept: target-aware sentiment

Ordinary sentiment tools say "this post is negative." We say "negative about whom?" One post can be positive about one target and negative about another.

Example

"Floods destroyed the village, so much grief, but the CM worked all night on relief" → negative about the flood (an issue), positive about the Chief Minister (a leader).

There's a second, separate field — stance: does the author back or oppose the target (in this post only). Hard rule (D1): we never infer the author's own party, religion, caste or voting intention — only "share of posts opposing Party X", never "share of Party-Y supporters".

The stages, in order

StageIn plain words
0 · Pre-filtersDedupe, spam-drop, script detection — cheap checks before spending AI money (drops ~15–30%)
1 · Language ID"What language is this?" — script rules → IndicLID → Hinglish detector
2 · Tier-1 LLMThe cheap model reads every post → structured JSON
3 · Tier-2 escalationA stronger model re-reads the hard ~15% (low-confidence, sarcastic, code-mixed, unclear targets)
4 · Post-processingLink entities, geotag, embed → topics, coordination (deterministic code)

Coordination: clusters, never "bots"

We deliberately removed "bot detection". Instead we find clusters of coordinated posting: near-identical text from ≥ 10 distinct accounts and ≥ 30 posts in a tight window, scored 0–100 (text similarity + timing), and analyst-confirmed before a client sees it. Wording is always "X% of today's negative volume belongs to a coordinated cluster" — never a list of named "bot accounts".

How we measure accuracy (the gold set)

This is the honest part — why our numbers are trustworthy. Why we need it:

  • It's the product's promise. We sell "published per-language accuracy", so we must measure it before selling (week 7, CP-3).
  • "Accuracy" is meaningless without human truth. The AI's confidence score is self-reported; only comparing against human-labelled posts tells us if it's actually right.
  • The frozen test set prevents self-deception. 25% is never shown during development, so we can't "teach to the test".
  • Gates + the human ceiling keep us honest about limits. Humans only agree on sarcasm ~30–50% of the time, so no machine can be "95% accurate on sarcasm" — we report it as a share, and cap the Hinglish gate at ~0.72 (best public benchmark ~0.75).

How we'll do it:

StepWhat happens
1 · RulebookWrite the annotation guideline (defines opinion vs news, sarcasm, stance — so annotators agree)
2 · SamplePull ~500 real posts per language (60% natural, 40% hard cases)
3 · Hire2–3 native speakers per language + a lead (vendors: Karya + 2 others, quoted week 0)
4 · LabelAnnotators see text only — no author handle, name or URL
5 · Check agreement25% triple-labelled; disagreements go to the lead; fix the guideline, not the model
6 · Split75% for tuning, 25% frozen test (assigned by a hash at creation)
7 · MeasureRun the AI on the frozen set → accuracy score per language
8 · Gate🟢 GREEN (live) · 🟡 AMBER (badge) · 🔴 RED (volume only)
9 · Keep watchingMonthly re-sample 200 posts/language; re-run the test set on every prompt/model change

Timeline: quotes week 0 · annotators week 2–4 · ~4,500 items by week 7 (CP-3) · the V8 pilot (200 posts × 9 languages × 3 models, blind) in weeks 5–7 picks the model and produces the first accuracy card. Cost: ~₹0.5–1.5 lakh (budget up to ₹1–3 lakh until real quotes).

Guardrails baked into the prompt

  • Prompt-injection protection: post text is treated as data, never instructions — hidden "ignore your rules" text can't hijack the AI.
  • Neutrality: treat every party symmetrically; never express the AI's own view.
  • Honesty: if it can't tell, it says so (low confidence + escalate) instead of guessing.

Cost (why this is affordable)

One AI read costs roughly $4–17 per 100,000 posts. The expensive part is labelling, not inference: ~₹0.5–1.5 lakh one-time for the gold set. Tier-2 (the strong model) is capped so it can't silently eat the budget.

The three iron rules (this part matters)

Rule 1No per-person political inference — ever (D1)
There is no column anywhere for a person's leaning, religion, caste, or an is_bot flag. Literally — a CI test scans the entire database schema for those names and fails the build if any appear. Authors are stored only as a scrambled hash.
Rule 2Raw text is perishable; scores are durable (D6, D29)
Every post gets an expiry date the moment it's stored (YouTube 30 days, others 90). An hourly purge deletes raw text — and every fragment (mentions, embeddings, search index). But the scores we derived (sentiment, emotion, topic, cluster id) contain no raw text and are kept forever.
Rule 3Author hashing (D1, D25)
Author identities are scrambled with one global secret key into a 64-character hash. We can count distinct authors without knowing who they are. The key is versioned — rotating it deliberately breaks all linkage.

How alerts actually work (why they're not noisy)

  • Compare against a seasonal baseline ("usual for this hour on this weekday"), not a flat average.
  • Require a minimum sample size + effect-size floor — a small entity can't page you over noise.
  • Use a z-score + confidence interval (is it really above baseline, or just luck?).
  • Have cooldowns (no re-alert every 5 minutes) and dedupe keys (a retry never double-sends).
  • AMBER/RED languages never fire share-based alerts (they'd be unreliable).

The hallucination guard (this is important)

The LLM that writes the brief is not allowed to make up numbers:

  1. Python builds a JSON of facts (exact numbers) — the LLM sees only that, never the database.
  2. The prompt says: use only these facts, refer to them as {"{{f1}}"}, never compute new figures, say "not available" if a fact is missing.
  3. Every number in the finished text is programmatically checked against the facts — a wrong number rejects the draft and it's regenerated; two failures → template summary (no prose) + flagged for the analyst.

The result: the prose can be imperfect, but the numbers can never be wrong — they're substituted, not generated.

The key legal uncertainty: DPDP "public data"

The DPDP Act exempts data a person made public themselves. That's our legal basis. But the boundary is untested:

  • ✅ Clearly exempt: a person blogging their own views.
  • ⚠️ Not clearly exempt: posts about a person by others; followers-only/semi-private spaces; inferred/derived data; content later deleted.

Our design response (D1, D10): aggregate-first, hashed handles, no per-person inference, provenance logged, honour deletions — we stay on the safe side of every grey area.

2Election law
Publishing "poll-like" outputs near elections is a criminal risk. The embargo switch exists to prevent it.
3DPDP inferred data
Combining scraped data with non-public data (CRM, purchased lists) pulls us inside the Act. We never do this.

The concierge pilot (file 28) — the key concept

Concierge = the machine does the repeatable work (collecting, labelling, grouping), and a named analyst does the rest by hand (picking narratives, writing the brief, checking the embargo). The client sees a brief and numbers — not a dashboard yet. This lets pilots start in week 6 instead of waiting for week 12.

  • Aggregate-first, no handles, no profiles.
  • No accuracy claims before CP-3 (end of week 7) — every brief says "early-stage labels, analyst-checked".
  • No vote prediction, no "poll" wording.
  • Manual embargo checklist on every brief.
  • A refusal is always logged.
